# l10n-improve · 回顾迭代（让框架越用越好）

> **职责**：错误不是浪费，是框架的燃料。本 skill 把使用中产生的三类数据（缺陷台账、裁决记录、抽核结果）提炼成**修订提案**，经人确认后版本化落地——术语表更厚、rubric 更准、skill 文档的坑册更长、工具修掉实测 bug。
> **设计立场**：这套框架是交付物而非黑盒——使用方的真实样例通过反馈包回流维护者，持续迭代（反馈通道见第 4 节）。

## 触发时机

- 每完成 **3-5 份报告**（例行回顾）
- 台账出现 **FAIL** 稿（`defect_log.py trend` 一眼可见）
- 评审理由抽核一致率低（<70%，评审被降级）
- 维护者索要反馈 / 大版本升级前

## 流程四步

### 1. 数据采集
```bash
python tools/defect_log.py trend --db wk/defect_log.db
```
再加：`wk/decisions.json` 全量裁决记录、理由抽核记录（交互点 4 产物）、使用者备注（`wk/notes.md`，随用随记）。

### 2. 错误模式提炼
从数据里找**重复**（单次是噪声，重复是模式）：
- 同 type 的 major 错误 ≥3 次 → 模式
- 同一术语反复进不确定列表 → 术语表缺口模式
- 抽核中评审「理由与分数不符」同类出现 → 评审 prompt/rubric 表述模糊
- 工具输出与人工判断系统性相悖 → 工具 bug 或口径缺陷

### 3. 归因与修订提案（交互点 7）
每个模式归因到四向之一，产出**结构化提案**（呈决策人确认，不静默改）：

| 归因 | 修订动作 | 走哪里 | 版本影响 |
|---|---|---|---|
| 术语表缺口 | 补条目/改译法 | `l10n-sediment` 回填 | glossary 内部版本 |
| rubric 盲区（某类错没被拦住/误拦） | 改维度定义或分类学 | 升 `rubric-vN` → **全量重校准**（l10n-calibrate 失效管理） | rubric 大版本 |
| skill 文档缺陷（流程步骤漏/坑没写） | 加坑册条目/改步骤 | 直接改对应 SKILL.md，记 CHANGELOG | 框架版本 +0.0.1（PATCH） |
| 工具缺陷 | 修 bug/改口径 | 改 tools/*.py，加自测样例，记 CHANGELOG | 框架版本 +0.0.1（PATCH）；skill 新增才是 MINOR(+0.1.0) |

**提案格式**（每条）：`模式（证据：N 次，例）→ 归因 → 改什么（diff 预览）→ 影响面（要不要重跑/重校准）`。

**为什么需要人**：修订改变的是全流程未来的行为，方向由决策人把关；尤其 rubric 类修订必须重校准，成本高，不能轻率。

### 4. 反馈包导出（回流维护者）
```bash
python tools/export_feedback.py wk/ --out wk/feedback_$(date +%Y%m%d).zip
```
脱敏导出（白名单规则内置于工具）：verdict 只留计数与 hash（剥离 span/note 原文片段）、decisions 的中文术语换不可逆指纹、calib 只留 idx 与布尔、台账数字原样。**notes.md 默认拒绝打包**（自由文本可能含客户内容——人工脱敏后显式 `--notes` 传入）。发给维护者，即可远程分析并出下一版。**不要用裸 zip 打工作区**——那会把客户原文片段带出去。

## 版本纪律

- 框架版本：`MAJOR.MINOR.PATCH`——rubric 变更/skill 新增 = MINOR，坑册/工具修复 = PATCH，结构性变化 = MAJOR；一切变更记入根 `CHANGELOG.md`（日期+变更+触发来源：「第 N 份报告回顾」或「反馈包 YYYYMMDD」）
- 修订后的 skill 若改变流程行为，`l10n-workbench` 总纲的阶段表/路由表同步更新——总纲与子 skill 不许各说各话
- **不静默原则**：任何修订未经交互点 7 确认不得写盘；已确认的修订当次生效并在下一份报告的任务书里声明「本稿起适用 vX.Y」

## 红线

- 单次错误不立模式（同 glossary 的 provisional 思想：重复才升格）
- 反馈包永不含客户正文/专名——错误模式与统计数字足够定位问题
- rubric 修订必触发重校准，没有「小改直接用」
