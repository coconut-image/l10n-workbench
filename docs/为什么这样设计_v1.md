# 为什么这样设计，而不是原来那样

> 本文回答一个问题：**表达层质量验证，为什么不用「一个大 skill」解决，而要做成手册+skill 集合+工具+人机交互点的体系？** 全部论据来自实测数据与一轮对抗式审查（36 项发现），不空谈理念。

## 一句话答案

因为要解决的不是「怎么翻译」，而是「**谁有权说这稿可以交**」——验收权问题需要的是可审计的信任机制，不是一个更大的 prompt。

## 1. 出发点：需求的真身

原始委托（AIT-20 转述）：「一次性把中文技术报告译成内部要求的英文、不做检查（最多一次极快检查，或抽检 10%，基本无错）」。

拆开看，最硬的约束不是质量，是**验收时间预算**：一次极快检查或 10% 抽检。走完一轮交付后发现：事实层（结构/数字/术语/不错位）机器全量检查已达标——**敢只抽 10% 的前提在事实层成立**；表达层没有任何机制替检查者筛过，所以还是得人逐段通读，「效率没上去」。

结论：缺的是给表达层造一个让签发人**敢只抽 10% 就放行**的信任机制。v2 的「独立会话 rubric 打分」方向对，但打分周围的护栏（校准/抽样/留档/沉淀）没有生产出来，所以阈值不敢定版、门禁立不住。

## 2. 为什么不是「把打分塞进原 skill」（单 skill 方案的五个结构性问题）

原 zh-en-docx-translation 的 SKILL.md 已经 513 行。把表达层验证塞进去会发生什么：

| # | 单 skill 的结构性问题 | 集合模式的解法 |
|---|---|---|
| 1 | **上下文膨胀**：翻译流程+评审规则+校准规则+资产规则全在一个文件里，每次触发全量加载；模型在超长指令下执行纪律的可靠性下降（这已被实测反复证明——原 skill 的「已知陷阱」表就是这么长出来的） | 按需加载：翻译时只载翻译规则，评审时只载评审规则；总纲只管路由 |
| 2 | **职责混杂**：翻译会话既当译者又当评审又当校准员，「自己审自己」（ISO 17100 明令禁止的形态）在单 skill 里物理上无法隔离 | 三会话分离是流程纪律：翻译/评审/校准各开独立会话，评审必须持校准证书，verdict 物理校验证书链 |
| 3 | **迭代牵连**：改一个评审阈值要动整个 skill，回滚和版本管理都是整块的 | 独立迭代：rubric 改版只触发重校准；工具修复记 PATCH；CHANGELOG 逐条可溯 |
| 4 | **人机交互点埋没**：需要人拍板的环节（裁决/签认/签发）写在流程文字里，跑起来最容易被跳过 | 交互点是一等公民：7 个拍板点各有「时机/人做什么/记录到哪/不放行条件」，工具层强制（不签字不出交付声明） |
| 5 | **门禁靠自觉**：文档写「必须校准」，但工具不验——对抗审查实测：空评审 JSON 能拿到 PASS、3 段迷你锚点集能上岗、改 rubric 后照常出分 | fail-closed 工具链：verdict/calibrate 对输入完整性、证书、hash 物理校验，缺一样拒出分 |

第 5 条不是假设——本文写就之前，三路对抗式审查（代码/文档一致性/红队绕过）在初版上实测出 36 项可绕过路径，全部修复后才有 v1.2.0。**单 skill 形态下这些防线没有落点**：一个 prompt 说「你必须校准」和一条工具链「无证书拒出分」，是两种东西。

## 3. 设计的三层分工（从 task-router 扩展）

| 层 | 特征 | 本框架实例 |
|---|---|---|
| 🧠 模型（语义） | 输入乱、要判断 | 翻译、润色、rubric 打分、裁决初筛 |
| ⚙️ 工具（执行） | 确定、可重放、零边际成本 | 7 个 .py（事实层另有 15 个既有脚本原样复用） |
| 📦 资产（知识） | 一次沉淀、永久生效、越用越厚 | 术语表、锚点集、rubric、缺陷台账、风格记忆 |

分工的判据很简单：**同输入必同输出的归工具，每次不一样的归模型，要跨报告活下来的进资产**。

为什么打分归模型、打分周围的归工具和资产——因为实测数据反复证明裸模型评分不可信：

- 全篇词汇重叠中位数 0.46（双引擎对照实测）→ 同义替换多，全篇机器对照 70% 误判
- 回译噪声率 ~93% → 统计信号当质量分必翻车
- 「句长标准差/被动比例」当目标会为了指标硬改（Goodhart）→ 表面指标只做下限参考

所以设计是：模型打分（它擅长的语义判断），但**上岗前考锚点**（一致率 ≥80%+critical 召回 100%，人标真值）、**打分绑理由**（≤2 分必须引原文 span，无理由作废）、**判定交给确定性代码**（阈值/密度/一票否决全在工具常量里，hash 留档防改）。

## 4. fail-closed：为什么门禁宁可误拦、不可放行

质量门的两种失败：放行了坏稿（假阴性） vs 拦住了好稿（假阳性）。前者进客户手里是事故，后者只是再跑一遍。所以整条判定链对「输入不完整」的默认反应是**拒绝**：

- 空评审 → 拒出分；抽样缺段 >5% → FAIL；缺维度 → 该段不通过；severity 写错 → 从严计 major
- 评审没证书 / 证书 rubric-hash 与当前不符 → 拒（rubric 改版必须重校准，历史不追溯）
- 判定绑定交付 docx 的 sha256 → PASS 判定不能移植给改过的稿子
- 台账拒绝同稿重复 seed（防「抽到过为止」）+ `--check-rubric` 对账（防出分后偷改）

这不是不信任使用者，是**让守规矩的人能自证清白**：每个 PASS 都可回溯到「哪个 rubric 版本、哪个评审者（持证）、哪份文件（hash）、哪个抽样（seed）」。

## 5. 一笔账（Before / After）

| | 人逐段通读（旧方式） | 工作台（新方式） |
|---|---|---|
| 首次成本 | — | rubric 签认 30 分钟 + 锚点标注 1 小时（一次性） |
| 每份 5 万字报告 | 通读 2-4 小时，且注意力后半程衰减 | 裁决 10 分钟 + 理由抽核 10 分钟 + 签发复核 10 分钟 |
| 判断依据 | 个人语感，无法复用 | 定版 rubric + 校准证书 + 缺陷台账（趋势可查） |
| 经验沉淀 | 在审校者脑子里，人走经验走 | 术语/风格/错误模式回填资产，下一份直接受益 |
| 审计 | 「我读过了」 | 每稿的判定报告：hash+证书+seed 全链可溯 |

## 6. 如实声明：本方案不解决什么

- **锚点「人工代打」**不可根除（AI 可生成自洽的标注对）——防线是理由抽核（交互点 4）+ 锚点选段机器字段可审计，抬高代打成本但非零
- **无分词器**的高频词扫描有少量碎片需人工分辨（掩码重计已把碎片压到接近零，非零）
- **AI 辅助口径**：质量保证是「机器全量+校准评审+抽样验收」，不等同 ISO 17100 的第二人通读——交付声明如实描述（这不是免责，是准确）
- **图片内文字**不在范围（单独立项按图计价）

## 7. 迁移路径（从 v2.4.0 单 skill 到工作台）

1. **保留**：既有 15 脚本、项目工作区（glossary/overrides/forbidden）、全部 override 译文库——一行不用改
2. **新增**：装 8 个 skill；首次走 `l10n-calibrate`（签认 rubric + 标锚点，锚点可直接从已交付报告中抽样——那些你已人工通读过的稿子就是现成真值）
3. **切换**：下一份报告起，翻译走原流程（阶段 0-9 不变），交付前多走 9.5（校准→评审→抽检）与 10-11（沉淀与签发）
4. **回退**：任何时候不想要表达层验证，退回只跑事实层门禁即可——工作台是叠加层，不是替换层
